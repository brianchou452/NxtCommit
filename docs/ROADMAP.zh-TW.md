# 路線圖

[English](ROADMAP.md)

本文件只收錄尚未完成的工作與刻意排除的目標。已發布的工作應記錄於 `CHANGELOG.md`；目前行為應記錄於 `ARCHITECTURE.md`；安全性要求應記錄於 `SECURITY.md`。

> **最高優先級阻礙：** CommonCommit 目前無法安全地執行任意第三方儲存庫，仍然是
> 以 fixture 為基礎的工作流程原型，而不是真正的 Pull Request 服務。
>
> 2026-08-06 的變化：每次執行各自的隔離機制**已經存在**，並在本機通過 SEC-00
> （140 次重複、七個攻擊向量、零洩漏 —— 見 `experiment-report.md`）。這移除了原本
> 的阻礙，但沒有移除那道關卡。距離執行真正的儲存庫還隔著三件事，而且性質各不相同：
>
> 1. **部署環境沒有邊界。** GKE Pod 內沒有 Docker daemon，`describeIsolation()`
>    在那裡回報 `process` —— 也就是 SEC-00 量到「20 次重複中有 20 次洩漏憑證」的那一
>    欄。這需要 per-run Kubernetes Job 或旁掛的 runtime，而它還不存在。
> 2. **AG-02 是未通過的 P0。** 它的圍堵那一半是通過的，但注入掃描器對「長得像攻擊
>    的無害文字」誤判率高達 47.1%，門檻是 5%；而一個被誤標的無害 issue 會擋掉一次
>    本來正確的執行。放寬匯入範圍只會把這個問題放大。
> 3. **計畫書自己的晉級檢查表**要求：在放寬匯入範圍前，必須重做威脅模型評估，並重新
>    執行每一項 P0。在內建 fixture 上通過，不會自動延伸到任意程式碼。

## 目前限制

| 領域 | 目前狀態 | 後果 |
| --- | --- | --- |
| 儲存庫執行 | 僅限內建 fixture | 無法執行 GitHub 匯入的專案，也無法將其轉成真正的 PR |
| 隔離 | 有 Docker daemon 且工作區可被 Docker 共享時，每次執行都有專屬容器（獨立的 PID／mount／network namespace）；探測回報 `process` 時（含 GKE Pod）只有應用層子行程控制 | 仍然不適合在共享環境中執行任意第三方程式碼：部署環境正是 `process` 那一種，而且放寬匯入範圍需要威脅模型評估 |
| 身分 | 沒有登入、授權或租戶模型 | 審查與認捐身分皆為模擬 |
| 上游整合 | GitHub 中繼資料僅供讀取 | 分支、PR、CI、標籤與發布只是本機產物或狀態 |
| 資料 | Kubernetes 中的 SQLite 與工作區位於 `emptyDir` | 重新啟動或 rollout 會遺失狀態；僅支援單一副本 |
| 驗證 | 在本機解析 Node test、Jest、Vitest、Mocha、pytest 與 Go test 輸出 | 沒有上游 CI 證據，也沒有逐項驗收條件的證明；部署環境具備的工具鏈仍比解析器所支援的範圍更窄 |
| 採用情況 | 發布後使用預載的示範數值 | 沒有真正的下游影響衡量 |
| UI 驗證 | 手動瀏覽器操作流程 | 沒有元件、無障礙或端對端瀏覽器測試套件 |
| Codex 封裝 | 本機開發會安裝 Codex CLI 相依套件；正式環境映像省略開發相依套件 | 在封裝修正並完成測試前，應將已部署的 Codex 模式視為不受支援 |

## 優先事項

### 跨領域 — 可量測的 LLM 協助

先在 public metadata 與 engine-owned evidence 擴大模型使用，不可先讓未隔離
repo 執行。分階段功能、Langfuse trace／score 契約、datasets、dashboards、
晉級 gates 與 isolated-worker 邊界定義於
[可量測的 LLM 擴充與 Langfuse 優化](LLM-OBSERVABILITY-PLAN.zh-TW.md)。
新增 LLM 流量上線前必須通過其中 OBS-01 P0；它不會取代下方 SEC-00、
SEC-01、AG-02 或 AG-04 gate。

### 1. 每次執行各自隔離，以及可執行的儲存庫匯入

這是處理真正儲存庫（而非 fixture）的先決條件。每次執行各自的邊界本身已經完成並經過
實測；剩下的是讓它在部署環境裡也存在，以及安全地放寬匯入範圍。

- ~~讓每次執行擁有 kernel 邊界，具備獨立的 PID／mount／network namespace。~~
  已完成：`server/engine/isolation.ts`，由 `npm run sec00` 驗證。殘餘風險記於
  `SECURITY.md` —— namespace 是 kernel 邊界，不是 hypervisor 邊界。
- ~~以決定性的方式清理每個工作區。~~ 已完成：`runLoop` 在 `finally` 中回收，因此
  異常結束的路徑也涵蓋在內。
- 將執行工作從 Web 行程移至佇列工作者，且每次執行使用一個隔離的工作負載 —— 這正是
  讓邊界在**叢集內**存在的關鍵，也正是目前缺少的那一塊。
- 使用不同的低權限身分、不掛載服務帳戶權杖、設定資源與磁碟限制，並將出口流量限制於指定目的地。
- 驗證主機、解析後位址、大小、commit、套件形態與授權政策後，才接受已固定版本的公開 HTTPS 來源。
- 收集結構化測試報告，而不是抓取 reporter 文字。
- 加入範圍讀取，並依截斷後的檔案內容拒絕寫入。

完成標準是：惡意儲存庫無法讀取伺服器密鑰、存取主機檔案系統、重新定義驗證、透過 symlink 或 clone 輔助工具逃逸，也無法保有無上限的磁碟或網路存取。

### 2. 身分與真正的 GitHub 交付

- 為認捐與審查加入使用者驗證及角色式授權。
- 安裝最低權限的 GitHub App。
- 只有在決定性閘門通過後，才建立真正的分支與 Pull Request。
- 透過已簽章的 webhook 接收上游 CI 證據。
- 將人工核准保留為硬性邊界；不要自動合併。
- 對齊本機產物狀態與遠端 PR、發布狀態。

完成標準是：每個審查決定都可歸屬於已授權的維護者，且每個上游操作都可稽核、可撤銷。

### 3. 持久化資料與水平擴充執行

- 在現有 store 邊界後方，以 Postgres 取代 SQLite。
- 將執行中工作的所有權移至持久化佇列與工作者租約。
- 讓重試、取消與復原在行程重新啟動後仍具冪等性。
- 持久保存產物與事件歷史。
- 定義備份、還原、保留與移轉程序。
- 以受限解析器，以及 secret manager 或 stdin 路徑，取代透過 shell 載入、以 argv 傳遞的 Kubernetes secret 初始化方式。

完成標準是：rollout 不會遺失任務狀態或執行中工作的所有權，且 API 可與工作者獨立擴充。

### 4. 更強的驗證證據

- 為每個宣稱支援的框架支援機器可讀 reporter，而非抓取文字敘述。
- 在每份產物中記錄測試命令、工具鏈版本、儲存庫 commit 與環境身分。
- 將驗收條件對應至明確證據，否則標示為未驗證。
- 為產生的相依套件、授權與過大產物加入政策檢查。

完成標準是：維護者不必信任執行器的敘述，也能從產物重現每一項聲稱的結果。

### 5. 真正的影響衡量與運算核算

- 以有來源依據的套件下載量與相依專案訊號，取代預載的採用數值。
- 在資料模型中區分已測量、延遲、無法取得與模擬的數值。
- 若點數不再只是示範單位，應將運算點數與供應商用量對帳。
- 在接受真實價值前，先定義託管、到期、取消與部分退款政策。

### 6. 產品與品質涵蓋範圍

- 針對認捐、執行、重設、審查、回饋與發布流程，加入雙語的瀏覽器端對端測試。
- 加入無障礙檢查與鍵盤操作流程涵蓋。
- 在外部用戶端開始依賴 API 前，先為 API 建立版本。

## 刻意排除的目標

- **不自動合併或推送至預設分支。** 即使真正整合 GitHub 後，仍強制要求人工審查。
- **不使用模型定義的驗證命令。** 受評估的代理不能自行決定何謂通過。
- **不將只有 prompt 的措施當成安全邊界。** 重大控制措施必須是決定性且經過測試。
- **不使用區塊鏈、可交易代幣或次級市場。** 運算點數不是貨幣。
- **不使用未標示的模擬。** 預載或腳本化資料必須與觀察所得的證據維持明顯區隔。
- **遺漏的測量值不得預設為零。** 未知不同於測量為零。
- **模型不得否決決定性證據。** 建議性審查可以提供資訊給人，但不能讓執行晉級或將其捨棄。
- **完成隔離前，不廣泛執行儲存庫。** 產品便利性不能凌駕威脅模型。
