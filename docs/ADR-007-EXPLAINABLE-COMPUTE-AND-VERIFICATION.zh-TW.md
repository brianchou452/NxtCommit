# ADR-007：伺服器掌管的運算估算與驗證檔案包

**狀態：** 已接受  
**日期：** 2026-08-13  
**決策者：** CommonCommit 維護者

## 背景

過去募資文案產生器可自行填入 `computeGoal`，伺服器只把數字限制在 2,400–50,000 點。確定性 Demo 使用 `LOC × 6 + issue 字元 ÷ 3`；只有 GitHub 中繼資料的匯入則依 issue 長度估算。這些方法都沒有公開分項、不確定性或歷史校正。審查成果雖有最終測試摘要與差異，卻沒有呈現放行變更前的所有實驗與確定性關卡。

## 決策

1. `server-heuristic-v2` 擁有 `computeGoal`。模型可以描述範圍與風險，但它填寫的數字會被丟棄。
2. 估算保存已觀測輸入、五個分項（基本、程式庫、issue、驗證、風險）、上下區間、信心、限制與校正資訊。
3. 有實測資料時使用 LOC 或檔案數；只有 GitHub 中繼資料時使用低信心且較寬的區間，並明確說明未量測檔案樹與測試時間。
4. 累積至少三筆可比較的成功執行後，以「實際／預估」中位數校正，倍率限制於 0.75–1.5；不足三筆時固定為 1。
5. 審查成果保存驗證檔案包：基準測試、每輪修改後測試、exit code、案例數、確定性關卡、驗收條件證據及來源。
6. 介面稱其為證據，不稱品質分數或保證，並固定呈現殘餘不確定性。

## 考慮過的方案

| 方案 | 評估 |
|---|---|
| 由募資 LLM 自行定價 | 彈性高，但未校正、不可重現，且讓執行者自己決定預算並不合理 |
| 固定點數下限 | 可預測，但忽略程式庫、issue、驗證與風險範圍 |
| 伺服器可解釋估算加有界校正 | 可重現、可檢查，也能從實際執行改善，而不把政策交給模型 |

## 影響

- 支持者可看到資助內容，以及區間寬窄的原因。
- Repo owner 可比較預估與實際用量，並檢查支撐變更的每次實驗。
- 舊的預載任務沒有歷史估算；介面仍可讀取，但不會虛構數字。
- 此方法仍是規劃模型，不是 provider 帳單。樣本足夠後，校正應再依語言、runner、測試框架與任務類型分群。

## 後續

- 按版本量測區間涵蓋率、MAPE、預算耗盡率與未使用點數比例。
- 只有引擎能證明驗收條件與測試對應時才新增逐項 mapping；不得從整套綠燈推論。
- 持續明確區分 provider token 用量與原型 credits。
